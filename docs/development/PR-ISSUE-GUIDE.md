# Issue·PR 작성 규칙

에이전트가 작업 PR을 올리고 검증과 두 리뷰 결과를 기록합니다. 일반 변경은 필수 검사를 통과하면 자동 병합하고, 사람 결정이 필요한 변경은 PR에서 확인합니다. 그래서 **사람이 위에서부터 30초 안에 상태를 파악하고, 필요한 곳만 더 읽는 구조**로 씁니다. 양식은 `.github/`의 템플릿이 기준입니다.

| 양식 | 파일 | 언제 |
| --- | --- | --- |
| PR | [pull_request_template.md](../../.github/pull_request_template.md) | 모든 PR |
| 작업 Issue | [task.md](../../.github/ISSUE_TEMPLATE/task.md) | 요구사항 구현, 문서 작업 |
| 버그 Issue | [bug.md](../../.github/ISSUE_TEMPLATE/bug.md) | 기대와 다른 동작 |
| 결정 요청 Issue | [decision.md](../../.github/ISSUE_TEMPLATE/decision.md) | 게이트: 사람이 정해야 하는 결정 |

## 누가 쓰는가

- **마스터가 작성합니다.** 개발 작업자의 `worker_done` 보고(변경 요약, 실행한 검사, 미실행 항목)와 독립 리뷰의 병합 결과를 합쳐 쓰므로 개발 작업자는 본문을 따로 올리지 않습니다.
- 개발 작업자는 보고에 PR 재료를 담습니다: 변경 요약, 검증 결과(명령·결과·환경), 실행하지 못한 검사와 이유, 커밋 해시, `Verified:` 줄.
- **트바 작업 브랜치 푸시와 Draft PR은 자동**으로 올립니다. 외부 Issue는 사용자가 승인한 경우에만 올립니다.

## 작성 규칙

1. **템플릿의 섹션을 지우지 않습니다.** 해당 없으면 `해당 없음 — 이유`를 적습니다. 안내용 HTML 주석(`<!-- -->`)은 최종 본문에서 제거합니다.
2. **"30초 요약"을 먼저 채웁니다.** 상태(병합 가능 / 조건부 병합 / 보류), 사람이 결정할 것, 위험도를 한눈에 보이게 씁니다.
3. **사실과 추정을 구분합니다.** 확인하지 못한 것은 `미확인`으로 적고, 통과했다고 쓸 때는 명령과 결과를 함께 적습니다.
4. **한국어로, 짧게.** 한 항목은 1~3문장입니다. 비교는 표를 씁니다. 긴 로그는 핵심 20줄 이내만 넣고 나머지는 링크합니다.
5. **제목**: PR은 `[F-010] 짧은 한국어 제목`처럼 요구사항 ID를 앞에 둡니다. 여러 개면 대표 ID 하나와 본문에 나머지를 적습니다. Issue는 템플릿 접두사 뒤에 ID를 적습니다(`[작업] F-010 …`, `[버그] F-011 …`). 결정 요청은 `[결정] 질문 한 문장`.
6. **붙이지 않는 것**: 키·토큰·`.env` 값, 위도·경도, 이메일 등 개인정보, 사용자 식별자. 화면 증거는 개인정보를 가려 첨부합니다.

## 자동으로 정한 결정

선택지가 있고 추천안이 있으면 에이전트는 묻지 않고 추천안으로 진행합니다(사람이 꼭 개입해야 하는 목록은 [오케스트레이션 절차](../../.claude/skills/orchestrate/SKILL.md) 참고). 그 결정은 PR의 "자동으로 정한 결정" 표에 **결정, 고려한 선택지, 추천 이유, 되돌리는 방법**으로 모두 적어서 사람이 나중에 검토하고 뒤집을 수 있게 합니다. 없으면 "없음"이라고 씁니다.

## 상태 판정 기준

| 상태 | 조건 |
| --- | --- |
| 병합 가능 | 관련 P0 인수 기준 충족, PR 마지막 커밋에 두 리뷰의 PASS와 필수 CI 통과, 미해결 중요 지적 없음 |
| 조건부 병합 | 남은 조건이 **사람의 행동만으로 해소**됨(예: 실기기 확인, 승인). 조건을 "30초 요약"에 명시 |
| 보류 | 코드·문서 수정이나 재리뷰가 필요함: 인수 기준 미충족, 중요 지적 미해결, 리뷰 커밋 불일치 |

## 위험도 기준

| 위험도 | 기준 | 사람 승인 |
| --- | --- | --- |
| 낮음 | 일반 문서(판정 기준 문서 제외), 내부 리팩터, 자동 검사 통과, 앱 동작 불변 | 요약 확인 |
| 중간 | 앱 동작·화면 변경 | 검증 결과와 리뷰 요약 확인 |
| 높음 | 인증·권한·개인정보 정책 변경, 운영 데이터 이전이나 삭제, 비용 발생, 사용자 요구사항 약화, 하네스·필수 CI 변경 | **병합 전 사람 승인 필수**, 되돌리는 방법 명시 |

## Issue 작성

- **작업**: 요구사항 ID, 포함/제외 범위, 시작 조건·행동·결과가 보이는 인수 기준을 적습니다. 완료 정의에 검증과 독립 리뷰를 넣습니다.
- **버그**: 재현 순서와 기대/실제 결과, 기기·OS·빌드를 적고 영향이 데이터 손실이나 권한 노출이면 "높음"으로 표시합니다.
- **결정 요청**: 질문은 한 가지, 선택지는 3개 이하, **추천과 이유를 반드시** 적습니다. 결정을 기다리는 작업과 기본값(결정하지 않을 경우)을 쓰고, 결정이 나면 사람이 "결정 결과"를 기록한 뒤 필요한 ADR을 갱신합니다.

## 에이전트 자체 점검

PR·Issue를 올리기 전에 확인합니다.

- [ ] "30초 요약"만 읽어도 병합 여부와 필요한 결정을 알 수 있다
- [ ] 모든 섹션이 채워져 있거나 `해당 없음 — 이유`가 있다
- [ ] 검증 결과에 실제 실행한 명령과 결과가 있고 미실행 항목이 분리돼 있다
- [ ] 독립 리뷰가 검토한 커밋 해시가 PR의 마지막 커밋과 같다
- [ ] 비밀값·좌표·개인정보가 없다
