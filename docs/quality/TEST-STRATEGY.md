# 테스트 전략

앱 초기화 후 **실제 실행해 본 명령**만 아래 표에 기입한다. 검증 기록에는 명령, 결과, 플랫폼·기기, 실행하지 못한 이유를 남긴다. 현재(문서 단계)는 모든 앱 검사가 **미실행**이다.

## 검사 종류

| 검사 | 대상 | 실제 명령 또는 절차 |
| --- | --- | --- |
| 타입 검사와 린트 | 프로젝트 기본 검사 | 초기화 후 기입 |
| 단위 테스트 | 거리 계산·점수·랭킹 정렬 규칙·입력 분류·검증 함수 | 초기화 후 기입 (후보: Jest/jest-expo) |
| DB 정책·집계 테스트 | RLS, `submit_review`, `get_ranking`, 초대 함수 | 초기화 후 기입 (후보: Supabase pgTAP) |
| 개발 빌드 및 실행 | 앱 설치, 첫 실행, 소셜 로그인, 네이버 지도 표시(Expo Go 불가) | 초기화 후 기입 |
| 실기기 확인 | iPhone에서 핵심 흐름과 오류 경로 | [실기기 체크리스트](RELIABILITY-CHECKLIST.md) |
| Android 확인 | 빌드와 핵심 흐름 스모크 (첫 구현 범위) | 플랫폼 범위 확정 후 기입 |

CI에는 로컬에서 확인 가능한 검사부터 연결한다. 핵심 검사가 추가되면 안전한 실패 입력(예: 201m 입력이 통과하면 실패)으로 검사 자체가 실패를 포착하는지 확인한다.

## 불안정한 테스트 규칙

불안정(flaky) 테스트는 건너뛰거나 sleep을 넣거나 통과할 때까지 재시도하지 않는다. 원인을 찾아 고친다. 찾지 못했을 때 P0 요구사항·보안·멱등성·경계값(199/200/201m 등)을 검증하는 테스트는 **삭제하지 않고** 사람에게 올린다. 그 밖의 테스트만 삭제할 수 있고 이유를 PR에 기록한다. 같은 검사가 3회 연속 실패하면 멈추고 사람에게 올린다.

## 단계 0 스파이크 확인 항목

구현 시작 전 한 개발 빌드에서 확인하고 결과를 PR에 남긴다: 네이버 검색 20개 케이스 품질(G3)·좌표 단위, 약관(G1·G2), 지도 라이브러리 빌드·표시(G4), Apple·Google 로그인과 같은 이메일의 별도 계정·nonce(G6, 1단계 착수 전), Edge Function에서 검색 호출(G5), 카카오·네이버 로그인 방식과 별도 계정(G6·G7, 1b 착수 전), 최근 로그인 기록 저장소(G8).

## 자동 vs 실기기 구분 원칙

- **자동**: 결정적 규칙(거리 경계, 집계, 정책, 멱등성, 분류, 응답 순서).
- **실기기**: OS 권한 팝업, 실제 GPS 정확도, 키보드(IME·검색 키), 딥링크, 통신 차단, 앱 종료·재실행, 두 계정 동시 사용, 화면 가독성.

## iPhone 연결 상태에 따른 검증

1. 변경한 인수 기준과 아래 매트릭스에서 필요한 실기기 항목을 먼저 고른다. 개발 서명·첫 설치, 실제 권한·GPS·통신 차단, 소셜 로그인·딥링크, 기기 화면과 입력 동작의 변경은 해당 흐름을 실제 iPhone에서 확인한다. 문서만 바꾸거나 자동 검사로 충분한 변경은 실기기 해당 여부와 근거를 PR에 기록한다.
2. iPhone 없이도 변경에 해당하는 린트·타입·단위·DB·통합 검사를 실제 프로젝트 명령으로 실행하고 리뷰와 CI를 진행한다. 199m·200m·201m 거리 판정, 권한 거부, 네트워크 오류·재시도는 준비된 모의 입력과 응답으로 검증하고 자동 검사 결과로 기록한다. 앱 초기화 전에는 문서와 저장소 검사를 진행한다.
3. `xcrun devicectl list devices`와 Mobile MCP 기기 목록으로 연결 상태를 확인한다. 연결되고 잠금 해제된 iPhone에서는 **Mobile MCP를 우선**한다. 화면 자동화가 막히면 Xcode로 개발 빌드를 설치하고 [실기기 체크리스트](RELIABILITY-CHECKLIST.md)를 실제 기기 조작으로 실행한다.
4. 기기 미연결·잠금 또는 도구 문제로 필수 실기기 검사를 하지 못하면 `실기기 미실행`으로 사유·남은 항목·대상 SHA를 남긴다. 병합을 보류하고 같은 Run과 Draft에서 기다리는 동안 다른 검증 가능한 작업을 진행한다. 테스트 실행 준비가 됐을 때에만 연결이나 잠금 해제를 요청하고 그 답을 받은 뒤 기존 Run에서 이어간다. 실기기가 필요 없는 변경은 필수 리뷰와 CI 통과 후 일반 병합 절차를 따른다.
