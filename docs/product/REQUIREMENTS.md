# 기능 및 비기능 요구사항

[PRD](PRD.md)의 첫 버전 범위를 독립적으로 확인할 수 있는 크기로 나눈다. 상태가 **제안**인 항목은 승인 전이며, 구현 전에 확정한다.

- 우선순위: P0 첫 버전 필수 · P1 첫 버전 포함 권장
- 검증: **자동** = 자동 테스트(단위·DB 정책 테스트), **실기기** = iPhone에서 직접 재현([체크리스트](../quality/RELIABILITY-CHECKLIST.md)), 구현 단계는 1 개인 → 2 그룹 → 3 방문 인증 → 4 지도 순서이며 모두 첫 버전 범위다. 단계 0은 코드 이전 점검(스파이크: 네이버 검색·지도·Apple·Google 로그인 개발 빌드 스모크, 카카오·네이버 로그인 방식 검증)
- 용어: **범위(scope)** = 내 랭킹 또는 특정 그룹 하나. **평가(review)** = 한 번의 방문에 대한 항목별 점수 1건.

## 계정

| ID | 사용자 상황과 기대 결과 | 우선순위 | 인수 기준 | 검증 방법 | 단계 |
| --- | --- | --- | --- | --- | --- |
| F-001 | 처음 앱을 연 사용자가 소셜 계정으로 로그인한다 [확정: 소셜 로그인] | P0 | 첫 화면에서 **Apple·Google**(1단계) 중 선택 → 기기 내장 로그인 창 → 완료 후 랭킹 탭 진입. 카카오·네이버는 F-050(1b단계). 사용자가 로그인 창을 취소하면 로그인 화면에 머물고 오류 문구 없이 재시도 가능. 인증 실패는 원인 구분 문구와 재시도. 앱 재실행 후에도 로그인 유지. 로그아웃 후 데이터 접근 불가. 같은 사람이 다른 수단으로 로그인하면 **별도 계정**이 생기며 로그인 화면이 이를 안내([ADR-002](../decisions/002-로그인-방식.md), 계정 합치기는 후속). Apple·Google ID 토큰은 nonce를 검증하고, 같은 이메일을 쓰는 Apple·Google 계정이 자동으로 합쳐지지 않는지 1단계 착수 전(ADR-002 G6)에 확인 | 자동(세션 처리) + 실기기 | 1 |
| F-002 | 사용자가 설정에서 계정을 삭제한다 | **P0** (스토어 요건 [확인 필요], 출시 전 필수) | 삭제 확인과 최근 재인증(로그인 후 N분 이내, 아니면 다시 로그인 [제안]) 후 계정·본인 평가·멤버십 삭제. 삭제는 서비스 키가 필요한 서버 함수가 수행하며 서버가 JWT를 검증해 확인한 본인만 삭제 가능(요청 본문의 사용자 ID는 쓰지 않음). 중간 단계(제공자 해지 → 데이터 정리 → Auth 삭제)가 실패해도 같은 요청을 재시도하면 이어서 완료되고 응답을 잃어도 성공으로 끝남. Apple 로그인 계정은 삭제 시 Apple 토큰 해지 포함 [확인 필요]. 마지막 멤버가 삭제하면 그룹도 삭제되고, 아니면 그룹은 유지되며 삭제한 사람의 그룹 평가는 그룹 랭킹에서 제거(그룹 규칙은 2단계에서 확인, 1단계는 개인 평가·Apple·Google 계정). **삭제 전에 발급된 토큰을 삭제 후 재제출해도 거부**(JWT가 만료 전이라도 RPC가 사용자 존재를 검사, 액세스 토큰 수명은 짧게 [확인 필요]). 삭제 후 로컬 캐시(랭킹·그룹 데이터)도 삭제 | 자동(DB) + 실기기 | 1 (그룹 규칙은 2) |
| F-050 | 카카오·네이버로도 로그인한다 [확정] | P0 | 로그인 화면에 카카오·네이버 버튼이 추가되고 각각 로그인 성공 시 랭킹 탭 진입. 취소·실패·제공자 오류 구분 문구. 서버가 세션을 발급하는 경우(네이버) **우리 앱용으로 발급된 것임을 증명하는 방식**(인가 코드를 서버가 client secret으로 교환하거나 토큰의 발급 대상 검증)으로만 세션을 발급하고, 위조·만료·다른 앱용 토큰·재사용·만료된 state와 로그인을 시작하지 않은 세션의 state는 거부(state는 시작한 앱 세션에 결속하고 한 번만 소비, PKCE 지원 시 사용 [확인 필요]). 사용자 식별은 제공자 사용자 ID로 하며 이메일로 기존 계정을 조회·연결하지 않음. 같은 이메일을 가진 다른 제공자 계정과 합쳐지지 않고 별도 계정이 됨. 최초 로그인 동시 요청(더블 탭)에도 계정이 1개. 반복 실패 요청은 제한. 제공자가 이메일을 주지 않아도 로그인 가능. 계정 삭제 시 제공자 연결 해제는 [결정 필요, ADR-002]. G7 결과가 불리하면 1b 범위 조정은 사용자가 결정 | 자동(거부 경로·중복 계정·이메일 불연결) + 실기기 | 1b |
| F-051 | 로그아웃 후 로그인 화면이 최근 사용한 로그인 수단을 알려 준다 [확정] | P0 | 로그인 성공 시 기기에 **제공자 종류만**(apple·google·kakao·naver) 저장(시각·이메일·토큰·사용자 ID는 저장하지 않음). 로그아웃·세션 만료 후 로그인 화면 상단에 **"최근에 Google로 로그인했어요"**(제공자 이름만 표시, 마스킹 이메일은 표시하지 않음)를 보이고 해당 버튼에 "최근 사용" 표시(다른 버튼도 사용 가능). 저장값이 없으면 **"이전에 가입한 방법으로 로그인해 주세요. 방법이 다르면 새 계정이 만들어져요."** 안내를 로그인 화면에 항상 표시. 로그아웃해도 저장값 유지. **계정 삭제는 서버 삭제가 성공한 뒤에만** 저장값을 삭제(서버 실패 시 유지하고 재시도 안내). 설정 화면에 현재 로그인 수단 표시. 서버에서 이메일로 가입 여부·수단을 조회하는 기능은 만들지 않음. 저장소 읽기·쓰기 실패해도 로그인은 동작. 다른 기기에서 계정을 삭제했거나 서버 삭제 응답을 받지 못한 경우 기기에 제공자 종류가 남을 수 있으며 이는 수용한 한계(제공자 이름만 저장) | 자동(저장·로그아웃 유지·삭제 순서·읽기 실패) + 실기기(로그아웃·세션 만료 후 표시, 설정 화면 표시, 재설치 후 동작 기록) | 1 (카카오·네이버 표시는 1b) |

## 검색과 식당 선택

기존 검색 문서의 원칙을 모바일에 맞춘다: **입력 중에는 지도·화면 기준 위치가 움직이지 않고, 선택을 확정했을 때만 이동하거나 집중한다.** 모바일에는 마우스 hover·↑↓·ESC가 없으므로 탭, 키보드 `검색` 키, 지우기(X) 버튼, 뒤로 제스처로 바꾼다.

| ID | 사용자 상황과 기대 결과 | 우선순위 | 인수 기준 | 검증 방법 | 단계 |
| --- | --- | --- | --- | --- | --- |
| F-003 | 입력 분류: 지역·역·관광지와 식당명·음식 키워드를 구분한다 | P0 | 서버가 결과 유형(`area` / `place`)을 판정해 반환. `강남역`, `역삼동`, `남산타워` → area, `스시오마카세`, `광화문국밥`, `파스타` → place. 분류 실패 시 place로 취급. 입력만으로 검색 기준 위치·화면이 바뀌지 않음 | 자동(분류 로직, 고정 입력 표) | 1 |
| F-004 | 식당·음식 입력 시 후보를 보여주고 탭으로 선택을 확정한다 | P0 | 입력 후 500ms debounce로 요청(IME 조합 중 요청 안 함, 이전 요청 취소). 후보 행에 **이름·주소·카테고리**를 표시해 같은 이름의 다른 지점을 구분. **네이버 지역 검색은 결과가 최대 5건이고 페이지네이션이 없으므로** 후보는 최대 5개이며, 5개가 모두 같은 이름이면 "지역명을 함께 입력해 보세요" 안내를 표시. 행 탭 = 확정(식당 요약 → 평가 화면). 키보드 `검색` 키 = 후보 목록을 결과 목록으로 전환(첫 항목 자동 선택 안 함 — 모바일엔 하이라이트가 없고 동명이점 오선택 위험). 후보 제목의 HTML 태그(`<b>`)·특수문자가 화면에 그대로 보이지 않음 | 자동(요청 타이밍, 응답 매핑, 태그 제거) + 실기기 | 1 |
| F-005 | 지역·역·관광지를 입력하면 확정 시에만 해당 지역으로 이동한다 | P0 | area 판정 시 후보 대신 "‘강남역’ 주변으로 이동" 행 표시. 탭/`검색` 키로 확정할 때만 검색 기준 위치가 바뀌고(1단계: 기준 지역 표시와 "지역명 + 맛집" 결과 최대 5건, 4단계: 지도 중심도 이동), 검색창 초기화. 확정 전에는 지도·기준 위치가 움직이지 않음. 폭넓은 주변 식당 목록은 공급자 한계로 이번 범위에 없음 [ADR-003](../decisions/003-식당-검색과-지도-공급자.md) | 자동 + 실기기 | 1(목록), 4(지도) |
| F-006 | 검색 중 문제를 이해하고 복구한다 | P0 | **빈 결과**: "검색 결과가 없어요" 문구와 입력 수정 안내(기존 문서의 미정 항목을 모바일에서는 메시지 표시로 제안). **통신 실패/타임아웃(8초)**: 오류 문구 + `다시 시도` 버튼, 입력값 유지. **쿼터 초과·서버 오류**: 일반 오류 문구. 재시도해도 결과 중복 표시 없음. 오래된 응답이 최신 입력 결과를 덮어쓰지 않음 | 자동(응답 순서) + 실기기(비행기 모드) | 1 |
| F-007 | Focus 모드(선택 식당 하나에 집중) | P0 | 후보 확정 시 해당 식당 1개만 카드로 표시하고 지도에 핀 1개 + 클로즈업. 지도 이동·확대로 결과가 바뀌지 않고 "이 지역에서 검색" 버튼 없음. 지우기(X), 검색어 편집, 다른 후보 선택, 뒤로 제스처로 해제 | 자동 + 실기기 | 4 |
| F-008 | 선택한 식당이 앱 안에서 고유하게 식별된다 | P0 | 같은 외부 장소를 여러 번 선택해도 식당 ID가 하나. 이름이 같고 주소가 다른 지점은 서로 다른 식당 ID. 클라이언트는 서버가 발급한 후보 ID로 `select_place`를 호출해 받은 식당 ID만 평가에 사용(임의 이름·좌표 전송 불가). 후보 ID는 발급받은 사용자만 만료 전에 쓸 수 있고 위조·다른 계정·만료 후 사용은 거부, 같은 후보를 다시 선택하면 같은 식당 ID를 반환 | 자동(DB 유니크 제약, 정책) | 1 |
| F-009 | 지도에서 식당 위치를 확인한다 [확정: 지도 포함] | P0 | 네이버 지도에 선택 식당 핀 표시. 지도 키가 없거나 지도 로딩에 실패해도 목록·평가 저장은 동작하고 지도 영역에 오류와 `다시 시도` 표시. 지도의 "내 위치" 기능은 첫 버전에서 제공하지 않아 위치 권한이 지도 때문에 요청되지 않음(F-042) | 자동(실패 시 대체 UI) + 실기기 | 4 |

## 평가

| ID | 사용자 상황과 기대 결과 | 우선순위 | 인수 기준 | 검증 방법 | 단계 |
| --- | --- | --- | --- | --- | --- |
| F-010 | 식당 평가를 항목별 점수로 저장한다 | P0 | 맛·가성비·분위기 각 1~5 정수 필수. 미입력·범위 밖(0, 6, 소수)은 저장 불가이며 어느 항목인지 표시. 상황 태그(혼밥·데이트·회식)는 0개 이상 선택. 저장 성공 시 내 랭킹으로 이동하며 해당 식당이 보임. 서버에서도 범위 검증 | 자동(검증) + 실기기 | 1 |
| F-011 | 저장을 재시도해도 평가가 중복되지 않는다 | P0 | 평가 화면이 열릴 때 요청 ID 생성. 같은 요청 ID로 여러 번(더블 탭, 통신 끊김 후 재시도, 앱 재시작 후 재전송) 저장해도 평가 1건. 재시도 응답은 최초 결과(방문 인증 결과 포함)와 동일. 다른 요청 ID로 같은 식당을 다시 평가하면 **재방문 평가**로 별도 저장(의도된 중복) | 자동(DB) + 실기기(저장 중 통신 차단) | 1 |
| F-012 | 평가를 수정·삭제하면 랭킹이 갱신된다 | P0 | 본인 평가만 수정·삭제 가능. 점수·태그 수정 후 내 랭킹과(그룹 평가면) 그룹 랭킹의 점수·순위가 즉시 갱신. 삭제 후 해당 식당의 평가가 0건이면 랭킹에서 사라짐. 그룹 변경은 불가(삭제 후 재작성). 수정은 방문 인증 배지를 다시 판정하지 않음 [제안]. 수정 가능한 열은 점수·태그뿐이며 `group_id`·배지·판정 열은 클라이언트가 바꿀 수 없음(직접 UPDATE 거부, `update_review` 서버 함수 사용). 그룹 평가의 수정·그룹 랭킹 갱신은 2단계에서 확인(1단계는 개인 평가) | 자동(집계) + 실기기 | 1 |
| F-013 | 저장 실패 시 입력을 잃지 않는다 | P0 | 통신·서버 오류 시 입력한 점수·태그를 유지하고 `다시 시도` 제공. 오류 중에 화면을 벗어나면 확인 후 폐기 | 실기기 | 1 |
