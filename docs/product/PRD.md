# 제품 요구사항 문서 — 트바(TB, trustBite)

- 상태: **초안 v0.3** (2026-11-24). 사용자가 확정한 항목과 제안·결정 필요 항목을 아래 표기로 구분한다.
- 표기: **[확정]** 사용자 요청에 명시됨 · **[제안]** 합리적 기본안, 승인 전 · **[결정 필요]** 담당자 답이 있어야 확정
- 참고 자료: 기존 웹 기획서(TrustBite 2차 기획서)와 검색 기능 문서는 **참고안**이다. 이 문서가 기준이며, 웹 기획서의 50m 반경·브라우저 위치 API·그룹 3차 일정은 이 문서로 대체한다. 변경 내역은 [부록 A](#부록-a-웹-기획서에서-바뀐-점)에 정리했다.

## 한 줄 소개 [확정]

트바는 혼자 또는 커플·친구·소규모 그룹이 다녀온 식당을 각자의 기준으로 평가하고, 다음에 어디를 다시 갈지 **내 랭킹** 또는 **우리 그룹 랭킹**으로 정하는 모바일 앱이다.

## 핵심 사용자

| 사용자 | 하고 싶은 일 |
| --- | --- |
| 자기 맛집 순위를 남기고 싶은 사람 | 다녀온 식당을 항목별로 빠르게 기록하고, 내 기준의 순위를 본다 |
| 함께 먹으러 다니는 커플·친구·소모임 | 같은 식당에 대한 각자의 평가를 한곳에 모아 우리 그룹의 순위로 재방문을 정한다 |

## 해결할 문제

- 일반 맛집 앱의 별점은 불특정 다수의 평균이라 **내 기준·우리 기준**과 다르다.
- 함께 다닌 곳의 평가는 메신저 대화와 개인 메모에 흩어져 있어 "다시 갈 곳"을 정하기 어렵다.
- 현재의 대안: 메모 앱, 지도 앱 즐겨찾기, 단체 채팅방. 순위와 그룹 합산이 없다.

## 핵심 흐름

### A. 개인 — 앱을 열어 첫 평가와 내 랭킹까지 [확정]

1. 앱 열기 → 소셜 로그인(첫 실행) → **내 랭킹** 탭(비어 있음, "첫 식당을 평가해 보세요")
2. 식당 찾기: 검색창에 식당명·음식 키워드 입력 → 후보(이름·주소·카테고리) 표시(네이버 검색은 후보가 최대 5개이므로 지역명을 함께 입력하도록 안내)
3. 후보 탭으로 식당 선택 확정 → 평가 화면
4. 맛·가성비·분위기 각 1~5점 입력, 상황 태그(혼밥·데이트·회식)는 선택 → 저장
5. 내 랭킹에 해당 식당이 점수순으로 나타남. 앱을 종료했다 다시 열어도 유지됨

목표: 설치 후 첫 평가 저장까지 **3분 이내** (성공 기준 참고).

### B. 그룹 — 만들기·참여 → 같이 평가 → 그룹 랭킹 [확정]

1. 그룹 만들기(이름 입력, 커플은 정원 2인 그룹) → 초대 링크 공유
2. 초대받은 사람은 링크를 열고(필요 시 로그인) 참여
3. 평가 화면에서 "나만 보기" 또는 **그룹 하나를 선택**해 저장 [확정, Q1]
4. 그룹 랭킹 탭에서 멤버들의 평가를 합산한 순위 확인. 화면 상단에 현재 범위("내 랭킹" / "○○ 그룹")를 항상 표시
5. 같은 식당을 그룹 A와 B에서 평가해도 두 그룹의 점수는 섞이지 않는다

### C. 방문 인증 [확정]

- 평가 저장 시 본인 GPS가 선택한 식당 좌표에서 **200m 이내**이면 그 평가에 '방문 인증' 배지를 붙인다.
- 배지는 **평가 단위**이며 그룹원에게 자동 공유하지 않는다. 사용자에게는 "평가를 남길 때 식당 근처에 있었다"는 뜻으로 설명한다.
- 범위 밖·권한 거부·낮은 정확도·좌표 누락 등 확인할 수 없는 경우에도 **평가는 배지 없이 저장**한다 [제안: 기본].

### D. 로그아웃 후 다시 들어오기 [확정]

1. 로그아웃되었거나 오랜만에 앱을 연 사용자가 로그인 화면을 본다.
2. 화면이 "최근에 Google로 로그인했어요"처럼 **마지막으로 사용한 로그인 수단**을 알려 주고 해당 버튼에 "최근 사용" 표시를 붙인다. 다른 수단도 선택할 수 있다.
3. 기록이 없으면(새 기기·앱 데이터 삭제) "이전에 가입한 방법으로 로그인해 주세요. 방법이 다르면 새 계정이 만들어져요." 안내를 보여 준다(문구는 F-051 기준). 로그인 수단이 다르면 별도 계정이 되며 계정 합치기는 후속이다 [제안].

## 화면 구성 [제안]

기존 기획서의 "맛집 탐색 / 나의 맛집" 2탭과 지도+리스트 조합은 후보로 참고하되, 첫 버전은 **식당 선택과 평가 저장을 빠르게 끝내는 것**이 우선이라 목록 기반 흐름을 먼저 완성하고, 지도는 같은 첫 버전 안에서 4단계로 붙인다.

| 탭 | 내용 | 첫 버전 |
| --- | --- | --- |
| 랭킹 | 상단 범위 선택(내 랭킹 / 그룹들) + 순위 목록 | 포함 |
| 찾기 | 검색 → 후보 → 식당 선택 → 평가 | 포함 (리스트 기반) |
| 그룹 | 그룹 목록, 만들기, 초대, 멤버 | 포함 |
| 설정 | 계정, 로그아웃, 계정 삭제 | 포함 |
| 지도 보기 | 네이버 지도에서 선택 식당 위치 확인, Focus 모드 클로즈업, 랭킹의 "지도로 보기"(범위별 핀) | **포함(구현 4단계)** [확정] |

세부 검색 동작은 [REQUIREMENTS](REQUIREMENTS.md) F-003~F-009에 있다.

## 첫 버전 범위

**포함**
- 소셜 로그인 [확정]: **Apple·Google**(1단계), **카카오·네이버**(1b단계, 구현 방식 검증 후) — [ADR-002](../decisions/002-로그인-방식.md)
- 로그아웃 후 로그인 화면에서 **최근에 사용한 로그인 수단을 알려 줌** [확정]
- 네이버 API 기반 국내 식당 검색(식당명·음식 키워드, 지역·역 이동)과 후보 선택 [확정: 네이버]
- 네이버 지도: 선택 식당 위치 확인, Focus 모드, 내 랭킹·그룹 랭킹 "지도로 보기" [확정: 지도 포함]
- 맛·가성비·분위기 항목별 점수 + 선택 상황 태그, 평가 수정·삭제
- 내 랭킹, 그룹 만들기·초대·참여, 그룹별 랭킹, 그룹 간 격리와 비멤버 차단
- 방문 인증 배지(200m)
- 계정 삭제(스토어 심사 대비) [제안]

**후속 범위 제안** (이번 버전에서 제외)

| 항목 | 이유 |
| --- | --- |
| 공개 맛집 랭킹 | 공개 범위·콜드스타트·신고 처리가 필요. 첫 버전은 개인=본인, 그룹=멤버만 |
| 사용자 trustScore와 가중치, 등급·포인트·팔로우 | 데이터가 쌓인 뒤 설계 가능 |
| AI 취향 요약·추천, ELO 상대평가 | 평가 데이터 규모 필요 |
| 사진·긴 리뷰 텍스트 | 저장소·신고·용량 정책 필요. 첫 버전은 점수와 태그 중심 |
| 가고 싶은 곳(북마크), 카카오톡 초대 연동, 로그인 수단 연동(여러 로그인 수단을 한 계정으로 합치기) | 첫 평가 루프 검증 후 |
| 지도 핀 색상 차등, 지도에서 주변 식당 폭넓게 탐색 | 네이버 지역 검색이 결과 최대 5건·반경 검색 없음이라 별도 설계 필요([ADR-003](../decisions/003-식당-검색과-지도-공급자.md)) |

**별도 제품 결정으로 남김 [결정 필요]**: 방문 인증 배지가 점수에 **가중치를 줄지**. 첫 버전은 배지를 표시만 하고 점수 계산에는 반영하지 않는다 [제안]. 가중치를 주면 위치 위조 유인이 생기고 랭킹 해석이 복잡해진다.

## 공개 범위 [제안]

| 대상 | 볼 수 있는 사람 |
| --- | --- |
| 개인 평가(그룹 미선택) | 작성자 본인만 |
| 그룹 평가 | 그 그룹의 현재 멤버만 |
| 방문 인증 배지 | 평가 작성자에게 표시. 그룹원에게는 배지 상태를 자동 공유하지 않음 [제안: 첫 버전은 작성자 본인 화면에만 노출] |
| 위치 좌표 | 서버에 저장하지 않음 [제안, ADR-005] ([ARCHITECTURE](../architecture/ARCHITECTURE.md#위치-인증-처리)) |

## 핵심 가정과 결정 필요 사항

| # | 질문 | 추천안 | 상태 |
| --- | --- | --- | --- |
| Q1 | '같이 간 평가'를 그룹 선택으로 연결할지, 같은 방문으로 묶을지 | 저장 때 **그룹 하나를 선택**. 같은 방문으로 묶지 않음(각자 자기 평가를 남김) | **확정** |
| Q2 | 그룹 평가가 내 랭킹에도 반영되는지 | **반영한다**(내가 남긴 모든 평가가 내 랭킹). 그룹 랭킹엔 그룹 평가만 | **확정** |
| Q3 | 그룹 점수·동점·재방문 처리 | 멤버별 평균 → 멤버 평균의 평균, 재방문은 모두 반영, 동점은 명시 규칙 | **확정** (탈퇴·삭제 시 처리는 자동 결정(추천안)) |
| Q4 | 기술 스택 | Expo + Supabase + 네이버 검색·지도 + 소셜 로그인 | **확정**: Supabase([ADR-001](../decisions/001-백엔드와-데이터-플랫폼.md) 승인), 네이버 검색·지도, 소셜 로그인(Apple·Google·카카오·네이버), 지도 포함, 앱 식별자 `com.joyanggi.trustbite`. 카카오·네이버 로그인 방식은 스파이크에서 검증 |

Q1~Q3의 세부 규칙은 [ADR-004](../decisions/004-랭킹-집계와-그룹-평가-연결.md)에 있다.

## 성공 기준 [제안]

첫 버전은 소규모(본인과 지인 5~10명) 검증이 목적이다. 수치는 시작값이며 첫 베타 뒤 조정한다.

| 지표 | 기준 | 측정 |
| --- | --- | --- |
| 첫 평가까지 시간 | 설치 후 3분 이내 | iPhone 직접 측정 |
| 첫 주 평가 수 | 사용자당 3건 이상 | 서버 집계 |
| 그룹 활성 | 생성된 그룹의 60% 이상에서 2명 이상이 같은 식당을 평가 | 서버 집계 |
| 데이터 정합 | 두 계정의 그룹 랭킹 불일치 0건, 비멤버 읽기 성공 0건 | 자동 테스트 + 실기기 |
| 안정성 | 저장 재시도로 인한 중복 평가 0건 | 자동 테스트 |
| 방문 인증 | 전체 평가 중 인증 비율과 미인증 사유 분포(권한 거부·낮은 정확도·범위 밖 등)를 본다. 목표 비율은 실기기 측정 후 정함 | 서버 집계(사유 코드). 좌표를 저장하지 않으므로 "식당 근처에 있었던 평가"의 분모는 측정하지 않음 |

## 플랫폼과 출시 범위

- Orca의 Mac 로컬에서 Expo·React Native·TypeScript로 개발하고 **iPhone에서 먼저 검증**한다 [확정].
- Android도 지원 대상으로 고려한다. 동시 출시 여부와 출시 일정은 **미정** [확정].

## 미결정 사항

- 방문 인증 정확도 기준(100m 제안)과 가중치 여부
- 초대 링크의 도메인(유니버설 링크) 보유 여부
- 네이버 검색·지도 데이터의 서버 저장 가능 범위와 지역 검색 5건 제한 대응(약관·품질 확인, [ADR-003](../decisions/003-식당-검색과-지도-공급자.md))
- 카카오·네이버 로그인 구현 방식과 제공자별 계정 처리([ADR-002](../decisions/002-로그인-방식.md))

상세 인수 기준은 [요구사항](REQUIREMENTS.md)에 기록한다.
