# ADR-003 식당 검색과 지도 공급자: 네이버

- 상태: **방향 확정(네이버 검색·지도, 지도는 첫 버전 포함 — 2026-11-24 담당자 요청) / 한계 대응과 약관 확인은 구현 전 게이트**
- 날짜: 2026-11-24
- 관련 요구사항: F-003~F-009, F-025, F-040

## 맥락

이전 초안은 카카오 검색을 추천했으나, 담당자가 **네이버 API로 검색과 지도를 구현**하고 **첫 버전에 지도를 포함**하기로 정했다. 따라서 이 ADR은 비교가 아니라 "네이버를 쓰되 알려진 한계를 어떻게 다룰지"를 정한다. 변경 비용이 큰 부분(식당 고유 키, 지도 라이브러리)을 공급자 교체가 가능하도록 격리한다.

## 확인한 사실 (2026-11 공식·공개 문서 조사)

| 항목 | 내용 |
| --- | --- |
| 지역 검색 API | NAVER API HUB 문서 기준: 결과 수 `display` 1~5(기본 1), `start`는 1만 허용 → **한 번에 최대 5건, 페이지네이션 없음**. 일일 호출 한도 25,000회 [확인 필요: 현재 한도] |
| 응답 | 제목(`<b>` 태그 포함), 카테고리, 주소, 도로명 주소, 전화번호 필드(값이 실제로 오는지 [확인 필요]), `mapx`(경도)·`mapy`(위도). API HUB 문서는 WGS84로 설명 [확인 필요: 실제 응답으로 검증]. **장소 고유 ID 필드 없음**. 반경·위치 편향·카테고리 코드 필터 없음. 좌표 단위(소수 vs 정수 스케일) [확인 필요: 응답 샘플로 검증] |
| 지도 | 커뮤니티 라이브러리 `@mj-studio/react-native-naver-map`: Expo config plugin 제공, **개발 빌드 필요(Expo Go 불가)**, 2.x는 New Architecture 전용(라이브러리 README 기준, Expo 문서상 SDK 55+는 비활성화 불가) [확인 필요: 현재 버전], 지도 클라이언트 ID 필요 |
| 확인하지 못한 것 | 검색 결과 저장·캐시 허용 여부, 지도 이용 과금·쿼터(NCP), 라이브러리의 현재 Expo SDK 호환 |

## 한계와 설계 대응

| 한계 | 영향 | 대응 |
| --- | --- | --- |
| 결과 최대 5건·페이지 없음 | 후보가 적고, 체인점이 많으면 원하는 지점이 안 나옴. "주변 식당 폭넓게 탐색" 불가 | 후보는 최대 5개로 설계(F-004). 5개가 같은 이름이면 "지역명을 함께 입력" 안내. 앱이 기준 지역명이 있으면 `"{지역명} {키워드}"`로 검색어를 조합해 편향(지역명 추출 방법은 스파이크에서 검증). **폭넓은 지도 탐색은 첫 버전 범위에서 제외** |
| 위치 편향·반경 검색 없음 | 현재 지도 중심 근처 식당을 우선할 수 없음 | 위 조합 검색 + 서버에서 지도 중심과의 거리로 재정렬(5건 안에서만) |
| 장소 고유 ID 없음 | `restaurants` 유일 키를 직접 만들어야 함 | `provider_place_key` = 정규화한 (이름 + 도로명 주소 [없으면 지번 주소])의 해시. 같은 건물에 동명 가게가 있는 경우의 보조 키는 스파이크에서 정한다(전화번호는 응답에 값이 오는지 확인하기 전까지 쓰지 않는다). 키 규칙을 바꿀 때는 `provider_place_key_version` 열로 구버전 키와 매핑하고 식당 uuid는 유지한다. 식당 ID는 내부 uuid로 유지해 평가 데이터는 키 규칙 변경에 영향받지 않게 한다 |
| 지역·역·관광지 구분 | 검색 API가 유형을 구분해 주지 않음 | 응답 카테고리(예: 지하철역·관광명소)와 행정구역 접미사(구·동·역) 규칙으로 서버가 판정 (F-003). 지역 중심 좌표 변환 수단(지오코딩 API 등)은 스파이크에서 [확인 필요] |
| 좌표 정확도 | 200m 방문 인증 경계에 영향 | 단계 3 실기기 측정으로 식당 좌표 오차 확인, 필요 시 인증 반경·표시 문구 조정 (R-19) |
| 지도 라이브러리가 커뮤니티 유지 | Expo SDK 업그레이드 때 깨질 수 있음 | 버전을 고정하고 업그레이드 전 스모크, 대체(WebView 기반 네이버 지도 JS) 가능성 기록 |

## 구현 전 게이트 (단계 0 스파이크, 개발자 작업)

| # | 확인할 것 | 결과에 따른 분기 |
| --- | --- | --- |
| G1 | 네이버 검색 결과(이름·주소·좌표)를 ① **우리 DB의 식당 행으로 저장**해도 되는지, ② 선택 전 후보를 서버에 **10분 임시 보관**(`place_candidates`)해도 되는지를 **각각 따로**(API HUB 이용약관 전문 확인) | 불가면: 최소 스냅샷 저장이나 재조회가 약관상 허용되는지 공급자 기준으로 확인하고, 허용되지 않으면 저장 항목 축소 방안과 함께 사용자에게 보고(법적·약관 판단). 이 설계는 이미 선택한 식당만 저장한다(`select_place`) |
| G2 | 검색 결과를 네이버 지도에 표시해도 되는지, 지도 이용 과금·쿼터 | 불가 시 지도 표시 범위 축소(진행 여부는 약관 판단이라 사용자 확인, 필수 개입 (f)) |
| G3 | 응답 좌표 단위와 `display=5` 응답의 실제 품질(한글 체인점·신규 가게·동명이점 20개 케이스, 합격 기준: 의도한 지점이 후보 5건 안에 나오는 비율 80% 이상 [제안]) | 품질이 기준 미달이면 보조 공급자 병행을 다시 검토 |
| G4 | `@mj-studio/react-native-naver-map` + 현재 Expo SDK 개발 빌드 + 소셜 로그인 모듈 동시 빌드 | 실패 시 라이브러리 버전 조정 또는 WebView 지도 |
| G5 | 서버(Edge Function)에서 네이버 검색 API 호출·키 보관 (앱에는 검색 키를 두지 않음) | — |

G1이 가장 중요하다. 현재 데이터 설계는 식당 스냅샷 저장을 전제로 하므로 G1이 불리하면 [아키텍처](../architecture/ARCHITECTURE.md#데이터-설계)의 `restaurants`를 줄인다.

## 영향과 재검토 조건

- 검색은 서버 한 곳(Edge Function)에 두어 공급자 교체 시 앱 코드를 바꾸지 않는다. 식당 ID가 내부 uuid라 평가는 유지된다.
- 앱 번들에는 지도 클라이언트 ID만 둔다(식별자 제한 설정 사용 [확인 필요]). 검색용 키는 서버 비밀로만 보관한다.
- 재검토: G3에서 후보 품질이 낮을 때(보조 공급자 병행 — 카카오 로컬 키워드 검색은 좌표·카테고리·페이지를 제공하는 것으로 조사됨이나 약관 미확인), 쿼터·과금이 예산을 넘을 때, 지도 라이브러리가 Expo 업그레이드를 따라오지 못할 때.
