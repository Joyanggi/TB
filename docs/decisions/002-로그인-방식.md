# ADR-002 로그인 방식: 소셜 로그인 4종과 최근 로그인 안내

- 상태: **방향 확정(2026-11-24 담당자 요청)**: Apple·Google·카카오·네이버 소셜 로그인, 최근 로그인 수단 안내. 카카오·네이버 구현 방식과 계정 처리 세부는 스파이크 후 확정
- 날짜: 2026-11-24
- 관련 요구사항: F-001, F-002, F-050, F-051, F-031, NF-003

## 맥락

그룹 공유에는 계정이 필요하다. 담당자가 Apple·Google로 시작하고 카카오·네이버도 지원하기로 했고, 로그아웃 뒤 "내가 무엇으로 가입했는지" 잊은 사용자를 돕는 기능을 요청했다. 로그인 수단이 여러 개가 되면 **같은 사람이 수단을 바꿔 들어와 계정이 갈라지는 문제**가 생기므로 이 기능은 선택이 아니라 필수에 가깝다.

## 제공자별 구현 (2026-11 조사)

| 제공자 | 확인한 사실 | 구현 | 단계 |
| --- | --- | --- | --- |
| Apple | Supabase가 기기 내장 로그인에서 받은 토큰으로 로그인하는 방식을 문서화. iOS에서 다른 소셜 로그인을 제공하면 Apple도 함께 제공해야 함 [확인 필요: 현재 심사 지침] | 토큰 방식 | 1 |
| Google | 같은 토큰 방식 문서화 | 토큰 방식 | 1 |
| 카카오 | Supabase 기본 제공 제공자. 문서는 웹 방식(인가 코드 → ID 토큰)과 OpenID Connect 활성화를 설명. 앱 내장 SDK 토큰 방식은 확인되지 않았고 한 토론글은 네이티브 앱 키로 불가하다고 함. 이메일 동의가 없으면 "이메일 없는 사용자 허용" 설정 필요 | 우선: Supabase 기본 방식(브라우저 로그인 후 앱 복귀). 불가 시 네이버와 같은 서버 검증 방식 | 1b |
| 네이버 | Supabase 기본 제공이 아님 | **인가 코드 방식**: 앱이 네이버 로그인으로 인가 코드를 받음 → Edge Function이 client secret으로 코드를 토큰으로 교환(우리 앱용 토큰임을 서버가 직접 증명) → 네이버 프로필 API로 제공자 사용자 ID 조회 → Supabase 사용자 조회·생성 → 앱에 세션 발급. 앱이 보낸 액세스 토큰을 그대로 신뢰하는 방식은 **사용하지 않음**(프로필 API는 발급 대상 앱을 확인해 주지 않을 수 있어, 다른 앱에서 발급된 피해자 토큰으로 로그인하는 공격 위험 — 리뷰 지적, 공식 문서로 확인 필요). 세션 발급 수단은 G7에서 확정 | 1b |

## 결정

1. 1단계는 **Apple + Google**, 1b단계에서 **카카오 + 네이버**를 추가한다. 1b는 첫 버전 범위에 포함한다. 단계 0 스파이크에서 카카오·네이버 방식을 검증한 뒤 착수한다.
2. **계정 정책(제안)**: 제공자마다 별도 계정이다. 이메일이 같아도 자동으로 합치지 않는다. 이유: Apple 이메일 가림 주소, 카카오·네이버 이메일 미제공 등으로 이메일이 신뢰할 수 있는 연결 키가 아니고, 잘못 합치면 남의 데이터에 접근하는 사고가 난다. 계정 합치기(연동)는 후속 범위다.
3. **최근 로그인 수단 안내(확정)**:
   - 로그인 성공 시 제공자 종류만 기기에 저장하고 로그아웃·세션 만료 후 로그인 화면에 "최근에 ○○로 로그인했어요"와 "최근 사용" 표시를 보인다.
   - 기기 단위 기록이다. 새 기기나 데이터 삭제 후에는 없을 수 있어 일반 안내를 둔다.
   - 서버가 이메일로 가입 수단을 알려 주는 조회는 만들지 않는다(계정 존재 노출·열거 공격).
   - 계정 삭제는 서버 삭제 성공 후 기록을 삭제한다. 시각·이메일·토큰·사용자 ID는 저장하지 않는다(화면에서 쓰지 않는 값은 수집하지 않음). iOS 보안 저장소는 앱 삭제 후에도 남을 수 있어 중고·공용 기기에서 이전 사용자의 로그인 수단이 보일 수 있으나 노출 정보는 제공자 이름뿐이다(G8).
4. 계정 식별은 `auth.users.id`로 하고 이메일에 의존하는 키를 만들지 않는다.

| G6 | 카카오: Supabase 기본 방식이 개발 빌드(앱 복귀 URL)에서 동작, 이메일 동의·검수 요건. **Supabase가 같은 이메일의 다른 제공자를 자동 연결하는지 확인하고, 자동 연결을 끄거나 우회해 "별도 계정" 정책을 보장**(**1단계 착수 전에** Apple·Google이 같은 이메일로 별도 계정이 되는지 먼저 확인하고, 1b에서 카카오(Supabase 기본)와 네이버(자체 구현)까지 포함해 4개 수단이 각각 별도 계정이 되는지 확인) | 불가하면 네이버와 같은 서버 검증 방식 |

## 영향과 재검토 조건

- 소셜 로그인과 지도는 네이티브 모듈이 필요해 **Expo Go 대신 개발 빌드**를 사용한다.
- 네이버 로그인의 세션 발급 코드는 인증을 우회할 수 있는 **보안 민감 코드**다. 토큰 검증 거부 경로 테스트(F-050)와 독립 리뷰를 필수로 한다.
- 계정 삭제(F-002)에는 제공자별 연결 해제가 포함될 수 있다 [확인 필요]. 삭제·로그아웃 뒤에도 이미 발급된 액세스 토큰(JWT)은 만료까지 유효할 수 있으므로(Supabase 동작 [확인 필요]) 서버 함수가 사용자 존재를 매번 검사하고 액세스 토큰 수명을 짧게 둔다.
- 재검토: 계정이 갈라져 데이터를 잃었다는 문의가 반복될 때(연동 기능 앞당김), 네이버 세션 발급이 위험하다고 판단될 때, 초대받은 사용자의 가입 이탈이 클 때.
