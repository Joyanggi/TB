# ADR-001 백엔드와 데이터 플랫폼: Supabase

- 상태: **승인** (2026-11-24, 담당자)
- 날짜: 2026-11-24
- 관련 요구사항: F-030~F-035, NF-001, F-011, F-020~F-024

## 맥락

그룹 공유, 로그인, 그룹별 랭킹에는 서버가 필요하다. 핵심 위험은 (1) 다른 그룹·비멤버의 평가가 읽히는 것, (2) 여러 사용자 평가를 범위별로 집계하는 랭킹의 정확성, (3) 1인 개발의 운영 부담이다.

## 고려한 선택과 판단 기준

기준: 비용, 유지보수 난이도, 그룹별 데이터 접근 제어, 랭킹 집계 적합성.

| 선택 | 평가 |
| --- | --- |
| **Supabase** (Postgres, Auth, RLS, Edge Functions) | 접근 제어를 DB 행 단위 정책으로 강제, 집계는 SQL, 관리형이라 운영 부담 작음. 무료 요금제는 개발에 충분하나 비활성 프로젝트 일시 중지 등 제약 |
| Firebase (Auth + Firestore) | 인증·실시간 편리. 그룹 랭킹 같은 조인·집계가 어렵고 읽기 과금 예측이 어려움 |
| 직접 서버(예: Node + Postgres) | 자유도 최고, 인증·배포·모니터링·정책 누락을 직접 관리해야 해 1인 첫 앱에 과함 |
| 기기 로컬 저장만 | 그룹 공유 불가 → 요구 불충족 |

## 결정과 이유

Supabase를 사용한다. 이유: 비멤버 차단을 클라이언트 코드가 아니라 데이터베이스가 보장하고, 그 정책을 자동 테스트로 검증할 수 있다. 랭킹이 단순한 SQL 집계이며, 스키마가 마이그레이션 파일로 저장소에 남는다.

## 영향과 재검토 조건

- 앱 번들에는 공개 키만 둔다. 서비스 키 유출 방지 규칙 필요.
- 무료 요금제 한도와 정책은 변동 가능 → 실제 가입·베타 직전 [공식 가격표](https://supabase.com/pricing)를 재확인하고, 베타부터 Pro로 전환해 일시 중지를 피한다.
- 재검토: 월 활성 사용자·DB 크기가 요금제 한도에 접근, 한국 리전 지연이 사용성에 영향(서울 리전 가용 여부 확인), 또는 RLS로 표현하기 어려운 권한이 생길 때.
