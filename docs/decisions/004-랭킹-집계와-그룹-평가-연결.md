# ADR-004 랭킹 집계와 그룹 평가 연결

- 상태: **Q1~Q3 확정(2026-11-24, 담당자 승인)**, 그룹·계정 삭제 시 평가 처리만 결정 필요
- 날짜: 2026-11-24
- 관련 요구사항: F-010~F-012, F-020~F-024, F-032, F-033, F-035

## 맥락

앱의 중심 기능은 내 랭킹과 그룹별 랭킹이다. 평가를 그룹과 어떻게 연결하느냐, 그룹 점수를 어떻게 합치느냐는 데이터 모델과 화면을 모두 바꾸므로 변경 비용이 크다.

## Q1. 그룹 평가의 연결 방식

| 선택 | 설명 | 장단점 |
| --- | --- | --- |
| **A. 평가 저장 때 그룹 하나를 선택 (확정)** | `reviews.group_id`가 NULL이면 개인, 아니면 그 그룹. 같은 방문으로 묶지 않음 | 단순한 모델·RLS, 격리가 명확. 같이 간 사람들이 각자 입력해야 하고 "같은 방문" 표시는 없음 |
| B. 같은 방문(visit)으로 묶기 | 방문 객체에 여러 사람의 평가가 달림 | "같이 간 기록" 표현이 풍부하나 방문 생성·참여·수정 권한이 복잡. 첫 버전 범위 초과 |
| C. 한 평가를 여러 그룹에 공유 | 중간 테이블 필요 | 평가 점수가 여러 그룹에 중복 반영되어 격리 요구와 충돌할 수 있음 |

추천 A: 같은 식당을 다른 날 다른 그룹과 가면 방문이 다르므로 평가도 따로 남기는 것이 자연스럽다. B는 후속에서 `visit_id`를 추가해 확장할 수 있다.

## Q2. 그룹 평가가 내 랭킹에 반영되는가

| 선택 | 설명 |
| --- | --- |
| **반영 (확정)** | 내 랭킹 = 내가 남긴 **모든** 평가(개인+그룹)의 평균. 한 번 평가하면 두 곳에 나타남 |
| 비반영 | 내 랭킹은 개인 평가만. 그룹용과 개인용을 따로 입력해야 해 입력 부담 2배 |
| 저장 때 선택 | 체크박스로 선택. 선택지가 늘어 첫 버전에 과함 |

추천 이유: 사용자가 "다녀온 곳을 내 기준으로 평가"하는 것이 앱의 출발이므로 그룹과 함께 간 곳도 내 기록이다. 단, 그룹 랭킹은 그 그룹 평가만 사용한다(F-022).

## Q3. 점수·동점·재방문 규칙 (확정, 아래 마지막 항목 제외)

- 평가 점수 = (맛 + 가성비 + 분위기) / 3. 항목 가중치 동일 [확정].
- **재방문**: 같은 사용자의 같은 식당·같은 범위 평가가 여러 건이면 **모두 평균**(최신만 쓰지 않음). 방문마다 감정이 다를 수 있고 삭제·수정으로 조정 가능.
- **개인 범위 점수** = 내 모든 평가 평균. **그룹 점수** = 멤버별 평균(그 그룹 평가만)을 구한 뒤 멤버 평균을 다시 평균(멤버 가중치 동일 — 자주 간 한 명이 좌우하지 않게).
- 평가한 멤버가 1명뿐이어도 순위에 포함하고 "1명 평가"를 표시.
- **동점**: ①평가한 멤버 수 ②맛 평균 ③가장 최근 평가 시각 ④이름 가나다 순. ①~③이 같으면 공동 순위("공동 2위").
- 표시는 소수 둘째 자리 반올림, 정렬은 반올림 전 값.
- 방문 인증 배지는 점수에 반영하지 않음(별도 제품 결정).
- 탈퇴한 멤버의 평가는 그룹 랭킹에서 제외, 그룹 삭제 시 그룹 평가는 작성자의 개인 평가로 전환 [제안, 결정 필요].

## 집계 구현 방식

`get_ranking(scope_type, group_id)` SQL 함수를 호출자 권한으로 실행. 개인 범위는 `user_id = auth.uid()` 조건을 명시, 그룹 범위는 `group_id = :g`(RLS가 멤버십 검사). 첫 버전은 저장 없이 매번 계산한다. 수정·삭제가 즉시 반영되고 불일치가 없다.

## 영향과 재검토 조건

- 재검토: 랭킹 응답이 NF-002(2초)를 넘을 때(머티리얼라이즈드 뷰·집계 테이블 도입), 같은 방문 묶기 요구가 베타에서 반복될 때(Q1-B), 방문 인증 가중치 도입 시(위조 유인 평가 선행).
