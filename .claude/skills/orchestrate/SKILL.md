# 트바 작업 오케스트레이션

이 절차는 사용자의 요청을 받은 마스터가 실행한다. Orca에서 Task·Dispatch ID가 포함된 요청을 받았다면 작업자다. 작업 범위와 완료 조건을 따르고, 주입된 명령으로 완료 보고를 보낸다.

## 시작과 판단

1. 버전에 맞는 `orca skills get orchestration`을 읽는다. 여러 단계가 의존하면 `--reference references/coordinator-loop.md`도 읽는다. Orca Mac 로컬에서 실행하며 다른 호스트에 작업을 보내지 않는다. 허용된 Orca 명령은 각각 단독 Bash 호출로 실행한다.
2. 사용자 요청, PRD, 요구사항, ADR, 현재 브랜치와 변경 내역을 확인한다. 기획 중이거나 미승인 범위인 아이디어는 요구사항·설계 초안과 검증으로 진행한다. 구현 요청에는 기능과 완료 기준을 정한 뒤 구현을 맡긴다. 아이디어가 기존 방향과 맞으면 가역적인 선택은 근거를 남기고 진행한다.
3. **사람이 반드시 개입해야 하는 경우에만** 사용자에게 묻는다(`gate-create`). 그 밖의 선택은 **선택지에 추천안이 있으면 묻지 않고 추천안으로 진행**한다. 추천이 없으면 마스터가 요구사항·ADR·비용·되돌리기 쉬움을 기준으로 가장 나은 안을 골라 진행하되, 아래 필수 개입에 해당하면 먼저 묻고 고를 근거가 없으면 (h)로 묻는다. **추천이 있어도** 출시 후 바꾸기 어렵거나 데이터 이전이 필요한 결정(앱 식별자·URL 스킴, 식별 키·토큰 형식, 공개 API·열 형태, 삭제·보관 정책)은 자동으로 정하지 않고 (a)로 묻는다. 아직 출시 전 초안 단계의 설계 문서는 되돌리기 쉬운 결정으로 본다. 작업자도 마찬가지로 아래 목록이 아니면 `ask` 없이 추천안으로 진행한다.

   **필수 개입(이 목록 밖은 묻지 않는다)**
   - (a) 제품 범위·방향·출시 범위 변경, 인수 기준 약화(기대 결과를 느슨하게 하거나 검증을 줄이는 변경) 또는 P0 하향, 앱 아이콘·로고 같은 제품 정체성의 최종 선택, 승인된 ADR·PRD와 충돌하거나 그것을 대체하는 선택(새 공급자·플랫폼 등)
   - (b) 비용이 발생하는 서비스·요금제 가입, 유료 프로그램(Apple Developer Program 등)
   - (c) 인증·서명·비밀값·계정: 외부 서비스 계정 생성, 키·인증서 발급, 권한 설정(`.claude/settings.json`, Codex 규칙 등) 변경
   - (d) 외부 공개·배포: 트바 이외의 저장소로 게시, 공개 범위 변경, 서비스 배포·스토어 제출, Issue 생성. 트바의 작업 브랜치 푸시·Draft PR 생성·보호된 `main`으로의 검증된 자동 병합은 사용자가 상시 승인했다. 이전에 사람의 결정이 필요한 변경은 결정을 받은 뒤 게시한다.
   - (e) 개인정보 수집·저장 항목의 추가·변경(위치·식별자·분석·크래시 SDK 포함, 실사용자 데이터 여부와 무관), 실사용자 데이터 처리 방식 변경, 프로덕션·실사용자 데이터에 영향을 주는 스키마·마이그레이션·삭제(개발·테스트 환경의 스키마 변경은 해당 없음)
   - (f) 법적·약관 판단이 필요한 사항(위치정보법, 공급자 약관 위반 가능성 등)
   - (g) 기기 연결·시스템 권한이 실제로 필요한 시점
   - (h) 3라운드 후에도 중요 지적이 남았거나 같은 검사가 3회 연속 실패했을 때, 또는 추천안을 도출할 수 없을 때

   **추천안 자동 진행 규칙**: 결정마다 (결정 내용, 고려한 선택지, 추천 이유, 되돌리는 방법)을 기록하고 PR 본문의 "자동으로 정한 결정"에 모은다. ADR 수준이면 ADR을 '제안' 상태로 남기고 진행한다. 사람이 나중에 뒤집을 수 있도록 되돌리기 쉬운 형태로 구현한다. 게이트와 관계없는 작업은 계속 진행한다. `gate-resolve`는 권한 설정상 사용자 승인 프롬프트가 뜨며, 사용자 답을 받은 뒤에만 호출한다.

   ADR의 **G1~G8은 단계 0 기술 확인 항목**이며 Orca 게이트와 다르다. 각 결과(통과/조건부/불가)를 PR에 기록한다(시점: G1·G3·G5·G8과 G6의 Apple·Google 부분은 1단계 착수 전, G6의 카카오 부분과 G7은 1b 착수 전, G2는 4단계 착수 전, G4는 단계 0 스파이크 중). G1·G6·G7이 불리하면 필수 개입 (a)·(f)로 사용자에게 묻는다.

## 역할별 에이전트·모델·노력치

사용자가 바꾸라고 할 때만 변경한다. `worker-start`에는 아래 값을 `--model`, `--effort`로 항상 명시한다(모델 ID는 Orca 카탈로그 기준).

| 역할 | `--agent` | `--model` | `--effort` | 비고 |
| --- | --- | --- | --- | --- |
| 마스터(요청 접수, Task 분배, 리뷰 병합·판단) | (현재 세션) | Opus — 프로젝트 `.claude/settings.json`의 `model: opus` | `high` — 프로젝트 `effortLevel` | 노력치는 명시해 사용자 설정 변화에 흔들리지 않게 함 |
| 개발 작업자 | `claude` | `claude-sonnet-5-5` | `medium` | 별도 worktree에서 구현 |
| 독립 리뷰 A | `codex` | `gpt-6.2-sol` | `high` | 읽기 전용 |
| 독립 리뷰 B | `claude` | `claude-sonnet-5-5` | `high` | 읽기 전용. 리뷰는 품질 관문이라 개발보다 노력치를 높게 둠 |
| 이미지·아이콘 등 그래픽 자산 생성 | `codex` | `gpt-6.2-sol` | `high` | 아래 자산 생성 절차 |

## 개발과 리뷰

1. 새 요청마다 `orca orchestration run-create --objective "<목표>"`로 Run을 만든다. `task-create`에 담당 범위, 허용한 변경, 검증 방법, 산출물과 완료 기준을 적는다. 작업마다 `git fetch origin main`으로 기준을 갱신하고 `origin/main`에서 새 worktree를 시작한다. 사용자 미커밋 변경은 공유 브랜치에 반영하지 않는다. 작업자에게 필요한 요구사항과 맥락은 Task에 포함한다.
2. 개발에는 `worker-start --task <id> --worktree new-child --name <작업명> --base-branch origin/main --setup skip --agent claude --model claude-sonnet-5-5 --effort medium`을 사용한다. 서로 의존하지 않고 동시에 편집해도 충돌하지 않는 작업만 별도 worktree에서 병렬로 시작한다. 마스터가 이전 작업 결과를 받아야 하는 일은 deps로 연결하거나 결과가 도착한 후 Task를 생성한다. 작업자에게 종료 시 테스트 결과와 정확한 커밋 또는 diff 경로를 `worker_done`으로 보고하게 한다. 개발 Task 스펙에는 다음을 항상 넣는다.
   - **커밋 작성**: [커밋·이슈·PR 작성 규칙](../../../docs/development/PR-ISSUE-GUIDE.md)을 읽고 `fix: 방문 인증 거리 계산 수정`처럼 영문 유형과 한국어 제목으로 커밋한다. 자산 작업자에게 커밋을 맡길 때도 같은 규칙을 Task에 명시한다.
   - **검증 후 보고**: `worker_done` 전에 `/verify` 절차를 **명시적으로** 수행한다(`verify` 스킬은 자동 호출되지 않는다). 커밋 메시지 본문에 `Verified: <실행한 검사>` 줄을 남긴다(`Co-Authored-By` 같은 귀속 줄보다 앞). `none`은 검증을 못 한 사유를 함께 적을 때만 쓴다.
   - **판정 기준 수정 금지**: 작업자는 `.claude/`, `REVIEW.md`를 수정하지 않는다(권한 설정 변경은 사용자 승인 대상). `docs/quality/`와 요구사항 인수 기준은 Task가 그 수정을 명시한 경우에만 고치고, 바꿨다면 이유를 보고에 적는다.
   - **불안정한 테스트**: 건너뛰기, sleep 추가, 통과할 때까지 재시도로 넘기지 않는다. 원인을 못 찾았을 때 P0 요구사항·보안·멱등성·경계값을 검증하는 테스트는 **삭제하지 않고** 3회 규칙으로 올린다. 그 밖의 테스트만 삭제할 수 있으며 이유를 기록해 보고한다.
   - **3회 규칙**: 같은 검사가 세 번 연속 실패하면 멈추고 실패 내용과 시도한 방법을 `ask`로 올린다.
   - **선택지와 추천**: 선택지가 있고 추천안이 있으면 묻지 않고 추천안으로 진행하며, 보고에 "자동 결정"(결정, 선택지, 이유, 되돌리는 방법)으로 적는다. `ask`는 필수 개입 목록이나 추천안을 낼 수 없을 때만 쓴다.
3. **이미지·아이콘 등 그래픽 자산 생성**은 `--agent codex --model gpt-6.2-sol --effort high` 작업자에게 맡긴다. Task에 용도·규격(해상도, 형식, 앱 아이콘이면 플랫폼 요구 크기)·저장 경로·사용할 수 없는 소재(타사 상표, 외부 저작물)를 적고, 보고에 원본 프롬프트·생성 조건과 산출 파일 경로를 포함하게 한다. 마스터가 결과 파일을 직접 열어 규격과 가독성을 확인한다. 앱 아이콘·로고처럼 제품 정체성이 걸린 최종 선택과 비용이 발생하는 외부 서비스 사용은 `gate-create`로 사용자 승인을 받는다. 자산을 만들 수 없으면 만들 수 없는 이유를 보고하게 한다.
4. **독립 리뷰는 변경이 남는 모든 작업에 Codex와 Claude를 병렬로 돌린다.**
   - **동시 시작**: 같은 기준 커밋·REVIEW.md·인수 기준·테스트 증거를 담은 동일한 Task 스펙으로 두 작업자를 한꺼번에 시작한다. A는 `--agent codex --model gpt-6.2-sol --effort high`, B는 `--agent claude --model claude-sonnet-5-5 --effort high`다. 서로 다른 Dispatch이며, 개발 worktree를 그대로 읽게 하고 파일 수정은 맡기지 않는다. 같은 worktree를 동시에 편집하는 작업자는 두지 않는다.
   - **기준은 base에서**: 리뷰 스펙에 기준 커밋(base)과 검토할 커밋 해시를 적는다. REVIEW.md·요구사항·ADR은 **base 커밋의 내용**을 기준으로 삼게 하고, diff가 `.claude/`, `REVIEW.md`, `docs/quality/`, 인수 기준을 바꿨다면 내용과 무관하게 별도 지적(높음)으로 보고하게 한다. 리뷰어는 시작과 종료 시 `HEAD` 해시를 확인한다. 같은 해시의 실질 리뷰가 끝났을 때에만 보고하고, 아래 자동 병합용 판정을 마지막 줄에 붙인다. 리뷰하는 동안 개발 worktree는 변경하지 않는다(개발 작업자는 대기·종료 상태). Claude 리뷰어는 읽기 전용 git(`git diff`, `git show`, `git rev-parse`)을 쓸 수 있고, `cd`를 붙인 복합 명령은 승인 프롬프트가 뜨므로 쓰지 않는다.
   - **자동 결정 검토**: 리뷰 스펙에 PR의 "자동으로 정한 결정" 표(없으면 마스터가 정리한 자동 결정 목록)를 주고, 필수 개입 목록에 해당하는데 자동으로 진행된 결정이 있는지, 되돌리기 어려운 결정이 섞였는지 검토하게 한다. 리뷰어도 diff에서 필수 개입 (a)~(h)에 해당하는 변경을 직접 찾아 보고한다(마스터 목록에 없는 결정을 잡기 위함).
   - **격리**: 각 독립 리뷰에서 한 리뷰어의 보고·터미널·Task 결과·메시지를 다른 리뷰어의 프롬프트, 메시지, Task에 넣지 않는다. 스펙에 "다른 리뷰어의 보고서·터미널·Task 결과·Run 메시지를 읽지 말고, 자기 보고만 `worker_done`으로 제출한다"를 명시한다. 마스터는 두 `worker_done`이 모두 도착한 뒤 아래 절차에 따라 근거를 전달할 수 있다.
   - **두 보고 종합**: 마스터는 지적을 양쪽 일치, 한쪽만 지적, 상충으로 정리한다. 한쪽만 지적한 사항은 마스터가 코드·문서·테스트를 확인해 채택 여부와 중요도를 판단한다. 상충한 사항은 아래 재검토에 건넨다. 채택한 지적을 구현 작업자에게 전달할 때는 마스터 정리본을 사용한다. 양쪽이 놓친 문제는 마스터가 직접 확인한다.
   - **이견이 있을 때 근거 재검토**: 두 보고의 `PASS/BLOCK`이 갈리거나, 처리 결과를 바꿀 정도로 같은 지적의 사실·중요도·수정 필요성에 의견이 갈린 경우에만 해당 SHA에서 한 번 실시한다. PR 번호가 없으면 아래 절차로 Draft PR을 먼저 연다. 두 Task를 만들기 전에 `/opt/homebrew/bin/tb-orca-merge --require-recheck --pr <번호> --sha <전체 SHA> --run <Run ID>`로 이 PR과 SHA의 재검토를 등록한다. 성공 응답의 `recheckRun`을 사용하고, 중간에 재개할 때도 같은 Run으로 돌아온다.
   - **재검토 전달**: 마스터가 쟁점별로 서로 다른 주장, 관련 파일·줄, 요구사항과 테스트 근거를 중립적으로 정리해 동일한 내용을 두 공급자에게 보낸다. 원문 보고와 작성자, 상대의 새 응답은 공유하지 않는다. 등록한 Run에 두 새 읽기 전용 Task를 만든 뒤 병렬로 시작한다. 각 Task 스펙에 다른 리뷰어의 보고·터미널·Task·Run 메시지에 접근할 수 없다는 격리 지침과 `TB-REVIEW-TARGET <전체 HEAD SHA>`, `TB-REVIEW-RECHECK <전체 HEAD SHA>` 단독 줄을 명시한다. 재시도는 같은 Task를 쓴다.
   - **재검토의 결론**: 리뷰어는 실제 diff·요구사항·테스트에 비춰 각 주장에 동의하거나 이의를 제기하는 이유와 남은 위험을 적고, 전체 PR에 대한 새 판정을 `worker_done`으로 제출한다. 재검토를 시작한 SHA의 병합에는 재검토 두 건의 `PASS`만 사용한다. 보고를 기다리는 동안에는 Draft를 유지한다. 한쪽이 `BLOCK`했거나 중요한 쟁점이 미해결이면 근거를 남기고 수정할 수 있는 항목을 구현 작업자에게 보낸다. 수정이 들어오면 새 SHA에서 두 독립 리뷰를 시작하고, 해결이 어려우면 기존 필수 개입 기준을 적용한다.
   - **리뷰의 유효 범위**: 리뷰 결과는 보고된 커밋 해시에서만 유효하다. 리뷰 중이거나 끝난 뒤 새 커밋이 생겼거나 해시가 다르면 그 결과로 완료 처리하지 않고 새 커밋을 다시 리뷰한다.
   - **라운드 상한**: 한 라운드는 "리뷰 → 채택한 지적 수정 → 재리뷰"이다. 최대 3라운드이고 "중요 지적"은 마스터가 채택한 높음·중간 지적이다. 필요한 근거 재검토는 그 SHA의 리뷰 안에서 한 번 진행한다. 첫 라운드 이후에는 새 diff 중심으로 재리뷰한다. 3라운드 후에도 중요 지적이 남으면 멈추고 접근을 바꿀지 사용자에게 묻는다(필수 개입 (h)).
   - **재리뷰**: 수정 diff는 위와 똑같이 병렬·격리로 다시 리뷰한다. 두 리뷰어에게는 같은 마스터 정리본(채택 항목, 수정 내용)만 줄 수 있고 서로의 원문은 주지 않는다.
   - **Codex 보고 전달 막힘**: Codex 작업자가 `worker_done` 전달 승인(샌드박스 `EPERM`, 승인 프롬프트)으로 멈추면 `escalation`이 온다. 이 경우 마스터가 `worker-read --dispatch <id>`로 작업자의 보고 본문(`worker_done`으로 보내려던 내용)을 읽어 그 보고로 취급하고, 결과에 "worker-read로 확보"라고 남긴 뒤 해당 세션을 `worker-stop`으로 종결한다(`worker-release`는 완료된 작업자만 해제된다). 본문이 잘렸거나 불완전해 보이면 그 리뷰를 인정하지 않고 같은 Task를 `--retry-of`로 한 번 재시작한다. 승인은 사용자 몫이므로 마스터가 대신 누르지 않는다. 먼저 `docs/development/WORKFLOW.md`의 Codex 규칙이 설치돼 있는지 확인한다.
   - **시작 실패**: Dispatch 상태와 Orca 복구 가이드를 확인한다. 사용량 한도로 확인되면 아래 **사용량 한도에서 재개**를 따른다. 그 밖의 재시도 가능한 시작 실패는 실패가 확정된 Dispatch에만 `--retry-of <실패한 dispatch ID>`를 붙여 같은 Task와 worktree에서 재시도한다.
   - **자동 병합용 보고**: 두 Task 스펙에 `TB-REVIEW-TARGET <전체 HEAD SHA>`를 단독 줄로 추가한다. 각 리뷰어는 실제 `worker_done` 본문의 마지막 줄에 `TB-REVIEW <전체 HEAD SHA> PASS` 또는 `TB-REVIEW <전체 HEAD SHA> BLOCK`을 붙인다. PASS는 차단할 문제가 없고 시작·종료 커밋이 일치하는 경우다. 파일 수정 목록은 비운다. `worker-read`로 확보한 본문은 진단에 쓰고, 자동 병합에는 정식 `worker_done` 보고를 다시 받는다.
5. 구현 보고를 받으면 `task-list --ready --brief`로 진행 가능한 작업을 갱신한다.
   - **게시 전 제목 확인**: 마스터는 푸시 전 커밋 제목과 PR 제목을 [작성 규칙](../../../docs/development/PR-ISSUE-GUIDE.md)에 맞춰 확인한다. PR 제목은 `feat: [F-040] 식당 방문 인증 추가`처럼 쓰고, PR 본문과 승인받아 올리는 이슈는 한국어로 작성한다.
6. **PR 발행**: 첫 검증 가능한 커밋을 `git push origin <SHA>:refs/heads/orca/<작업명>`으로 보내고 `gh pr create --repo Joyanggi/TB --base main --head orca/<작업명> --draft --title ... --body-file ...`로 Draft PR을 만든다. 이미 같은 브랜치의 PR이 있으면 재사용한다. `docs/development/PR-ISSUE-GUIDE.md`와 템플릿으로 내용·검증·미실행 항목·사람의 결정이 필요한 사항을 정리한다. 공개 PR 본문에는 비밀값·개인정보를 넣지 않는다. 같은 브랜치에 새 커밋을 푸시할 때마다 기존 리뷰 판정을 무효로 하고 새 SHA를 리뷰한다.
7. 여러 브랜치를 통합하는 경우 먼저 별도 통합 worktree에서 정확한 커밋들을 합치고, 합친 결과에 대해 검사와 최종 리뷰(위 병렬 리뷰)를 한다. 중요 지적은 구현 작업자에게 전달하고 변경된 검사와 리뷰를 다시 실행한다. 현재 권한 및 환경에서 확인하지 못한 것은 결과에 명시한다. 통합한 최종 SHA를 PR에 올리고 그 SHA에 대해 두 리뷰를 받는다.
8. **자동 병합**: 열린 제품 결정과 미통과 검사가 없고 두 리뷰가 같은 SHA를 통과시켰으면 마스터는 맥에 설치된 검토 완료 병합 실행기로 `/opt/homebrew/bin/tb-orca-merge --pr <번호> --sha <전체 SHA> --run <Run ID> --claude <Dispatch ID> --codex <Dispatch ID>`를 실행한다. 이견 재검토가 있었으면 그 두 Dispatch ID를 전달한다. 스크립트는 보존된 두 보고와 GitHub 보호 규칙을 검사하고 상태 체크를 게시한 뒤 squash 자동 병합을 요청한다. GitHub가 CI도 통과한 경우에만 병합한다. `main` 변경으로 작업 브랜치가 뒤처지면 최신 `origin/main`을 반영하고 새 SHA에서 다시 검사·리뷰한다. 하네스·권한·CI·판정 기준·운영 DB 마이그레이션 변경과 별도 사람 결정이 필요한 PR은 Draft로 남기고 사람에게 넘긴다. 배포는 별도 요청에 따른다.

   - **필수 실기기 확인**: 해당 SHA의 필수 실기기 검사가 미실행이면 병합 실행기 호출을 보류하고 같은 Draft에서 [검증 절차](../verify/SKILL.md)를 완료한다.

## 사용량 한도에서 재개

1. Claude 또는 Codex의 계정 사용량 한도가 확인되면 해당 작업을 대기 상태로 다룬다. 공급자, 알 수 있는 재설정 시각, Run·Task·Dispatch ID, worktree, 마지막 체크포인트, 리뷰 대상 SHA를 내부 Run 기록에 남긴다. 작업 초과로 실패 판정을 내리거나 테스트 실패 횟수·리뷰 라운드를 올리지 않는다. 컨텍스트 한계는 채팅 맥락 정리나 체크포인트로 복구하고, 일반 서버 오류·인증 실패는 각 원인으로 처리한다. 429만으로 계정 한도를 단정하지 않는다.
2. 마스터와 Claude·Codex 워커는 Orca **채팅**으로 실행한다. 맥의 **설정 → 채팅 UI → 사용 한도가 재설정되면 채팅을 자동으로 계속하기**를 켜고 Orca와 해당 채팅을 열어 둔다. Orca가 대기 표시를 한 채팅은 기존 세션에서 재개하도록 둔다. 대기 중에는 해당 worktree를 절전·정리하지 않고 탭과 Dispatch를 유지한다. 마스터가 사용 가능하면 한도와 관계없는 작업을 진행한다. 두 공급자가 모두 멈췄다면 각각의 재개를 기다린다.
3. 자동 재개가 동작하지 않으면 Orca가 제공하는 실제 한도 해제 정보부터 확인한다. 재설정 시각을 모르거나 세션이 실행 중인지 불확실하면 기존 상태를 보존한다. 해제가 확인되면 마스터는 같은 채팅에서 이어가며 `run-show --id <Run ID>`와 `task-list --run <Run ID>`로 대기 중인 작업을 찾는다. 워커가 멈췄으면 마스터가 해당 Dispatch ID로 `worker-show`와 `worker-read`를 실행하고, 살아 있는 채팅은 기존 Dispatch에서 이어간다. 실패가 확정되고 그 채팅을 재개할 수 없는 경우에는 Orca 복구 가이드에 따라 `worker-start --environment local --run <Run ID> --task <Task ID> --retry-of <실패한 Dispatch ID>`에 기존 worktree·공급자·모델·노력치 옵션을 다시 지정한다. 새 작업자는 마지막 커밋과 미커밋 변경을 먼저 확인한다.
4. 한도 대기 중에는 사용자가 추가 요금을 쓰거나 계정을 바꾸도록 요청하지 않는다. 재로그인·앱 재실행처럼 직접 조작해야 자동 재개를 복구할 수 있을 때만 해당 조작을 요청한다. 두 공급자 모두 최종 SHA의 정식 `worker_done`을 제출할 때까지 Draft를 유지한다. 다른 쪽의 유효한 리뷰는 같은 SHA에서 이어서 사용한다.

## 완료 보고와 재개

- 작업자를 시작한 뒤 턴을 끝낸다. Orca가 보낸 완료·질문 메시지로 재개한다. 채팅에 본문이 오면 처리하고, `check` 명령을 안내받았을 때만 실행한다. 백그라운드 메일을 가져오는 폴링 스크립트는 사용하지 않는다.
- 판단할 수 있는 작업자 질문은 바로 답한다. 실패한 Task는 성공으로 기록하지 않는다. 시작 실패와 재시도는 위 "시작 실패" 규칙을 따른다. 실패 원인을 확인해 가능한 범위에서 고치고, 응답이 불분명한 실행은 버전에 맞는 복구 가이드에 따라 기존 상태를 확인한다.
- [검증 절차](../verify/SKILL.md)에서 해당 변경의 필수 실기기 검사가 대기 중이면 같은 Run과 Draft를 유지한다. 기기 없이 할 수 있는 검사·리뷰를 먼저 진행하고, 실기기 체크리스트를 실행할 준비가 되면 사용자에게 연결·잠금 해제 등 필요한 조작만 요청한다. 해당 SHA의 필수 검사 증거가 생기면 기존 PR에서 이어간다.
- 최종 응답에는 PR 링크와 GitHub 병합 상태, 결과 커밋, 검사·두 리뷰 결과와 확인하지 못한 항목을 짧게 적는다. 자동 병합 신청과 병합 완료를 구분한다. 실기기 검증이 남았다면 연결이 필요한 시점을 알려준다.

## 읽기 전용 연결 시험

사용자가 오케스트레이션 자체의 연결 시험을 요청하면 위의 제품 작업 대신 같은 worktree에서 읽기 전용 작업자를 시작한다. Claude 작업자(`claude-sonnet-5-5`, `medium`)와 Codex 작업자(`gpt-6.2-sol`, `high`)를 서로의 결과를 보지 않게 병렬로 시작하고 각자의 `worker_done` 수신 여부를 확인한다. 시작 실패 시 재시도 절차도 시험한다. 시험은 파일 수정 없이 진행하고 두 보고의 수신 여부를 요약한다.
