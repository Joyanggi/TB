# 트바 작업 오케스트레이션

이 절차는 사용자의 요청을 받은 마스터가 실행한다. Orca에서 Task·Dispatch ID가 포함된 요청을 받았다면 작업자다. 작업 범위와 완료 조건을 따르고, 주입된 명령으로 완료 보고를 보낸다.

## 시작과 판단

1. 버전에 맞는 `orca skills get orchestration`을 읽는다. 여러 단계가 의존하면 `--reference references/coordinator-loop.md`도 읽는다. Orca Mac 로컬에서 실행하며 다른 호스트에 작업을 보내지 않는다.
2. 사용자 요청, PRD, 요구사항, ADR, 현재 브랜치와 변경 내역을 확인한다. 기획 중이거나 미승인 범위인 아이디어는 요구사항·설계 초안과 검증으로 진행한다. 구현 요청에는 기능과 완료 기준을 정한 뒤 구현을 맡긴다. 아이디어가 기존 방향과 맞으면 가역적인 선택은 근거를 남기고 진행한다.
3. 제품 방향·출시 범위 변경, 실제 사용자 데이터나 개인정보 처리 방식 변경, 비용이 발생하는 서비스, 배포·외부 공개, 인증·서명, 되돌리기 어려운 데이터 변경(**DB 스키마·마이그레이션·RLS 정책·식별 키 규칙 변경 포함**)처럼 명시적 결정을 받아야 할 때만 사용자에게 묻는다. 되돌리기 어려운 변경에서는 작업자가 멈추고 선택지와 추천을 함께 올리게 한다. `gate-create`로 해당 후속 Task를 막고, 확정할 질문·선택지·추천 이유를 함께 제시한다. 사용자 답을 받을 때만 `gate-resolve`로 해제한다. 기기 연결이나 시스템 권한이 실제로 필요할 때는 그 시점에 알린다. 게이트와 관계없는 작업은 계속 진행한다.

## 역할별 에이전트·모델·노력치

사용자가 바꾸라고 할 때만 변경한다. `worker-start`에는 아래 값을 `--model`, `--effort`로 항상 명시한다(모델 ID는 Orca 카탈로그 기준).

| 역할 | `--agent` | `--model` | `--effort` | 비고 |
| --- | --- | --- | --- | --- |
| 마스터(요청 접수, Task 분배, 리뷰 병합·판단) | (현재 세션) | Opus — 프로젝트 `.claude/settings.json`의 `model: opus` | `high` — 프로젝트 `effortLevel` | 노력치는 명시해 사용자 설정 변화에 흔들리지 않게 함 |
| 개발 작업자 | `claude` | `claude-sonnet-5-5` | `medium` | 별도 worktree에서 구현 |
| 독립 리뷰 A | `codex` | `gpt-6.2-sol` | `high` | 읽기 전용 |
| 독립 리뷰 B | `claude` | `claude-sonnet-5-5` | `high` | 읽기 전용. 리뷰는 품질 관문이라 개발보다 노력치를 높게 둠 |
| 이미지·아이콘 등 그래픽 자산 생성 | `codex` | `gpt-6.2-sol` | `high` | 아래 자산 생성 절차 |

## 개발과 리뷰

1. 새 요청마다 `orca orchestration run-create --objective "<목표>"`로 Run을 만든다. `task-create`에 담당 범위, 허용한 변경, 검증 방법, 산출물과 완료 기준을 적는다. 사용자 미커밋 변경은 공유 브랜치에 반영하지 않는다. 작업자에게 필요한 요구사항과 맥락은 Task에 포함한다.
2. 개발에는 `worker-start --task <id> --worktree new-child --name <작업명> --setup skip --agent claude --model claude-sonnet-5-5 --effort medium`을 사용한다. 서로 의존하지 않고 동시에 편집해도 충돌하지 않는 작업만 별도 worktree에서 병렬로 시작한다. 마스터가 이전 작업 결과를 받아야 하는 일은 deps로 연결하거나 결과가 도착한 후 Task를 생성한다. 작업자에게 종료 시 테스트 결과와 정확한 커밋 또는 diff 경로를 `worker_done`으로 보고하게 한다. 개발 Task 스펙에는 다음을 항상 넣는다.
   - **검증 후 보고**: `worker_done` 전에 `/verify` 절차를 **명시적으로** 수행한다(`verify` 스킬은 자동 호출되지 않는다). 커밋 메시지 마지막 줄에 `Verified: <실행한 검사 또는 none>`을 남긴다.
   - **판정 기준 수정 금지**: `.claude/`, `REVIEW.md`, `docs/quality/`, 요구사항 인수 기준은 마스터 승인 없이 수정하지 않는다. 수정이 필요하면 이유와 함께 `ask`로 요청한다.
   - **불안정한 테스트**: 건너뛰기, sleep 추가, 통과할 때까지 재시도로 넘기지 않는다. 원인을 못 찾으면 테스트를 삭제하고 이유를 기록하며 보고한다.
   - **3회 규칙**: 같은 검사가 세 번 연속 실패하면 멈추고 실패 내용과 시도한 방법을 `ask`로 올린다.
3. **이미지·아이콘 등 그래픽 자산 생성**은 `--agent codex --model gpt-6.2-sol --effort high` 작업자에게 맡긴다. Task에 용도·규격(해상도, 형식, 앱 아이콘이면 플랫폼 요구 크기)·저장 경로·사용할 수 없는 소재(타사 상표, 외부 저작물)를 적고, 보고에 원본 프롬프트·생성 조건과 산출 파일 경로를 포함하게 한다. 마스터가 결과 파일을 직접 열어 규격과 가독성을 확인한다. 앱 아이콘·로고처럼 제품 정체성이 걸린 최종 선택과 비용이 발생하는 외부 서비스 사용은 `gate-create`로 사용자 승인을 받는다. 자산을 만들 수 없으면 만들 수 없는 이유를 보고하게 한다.
4. **독립 리뷰는 변경이 남는 모든 작업에 Codex와 Claude를 병렬로 돌린다.**
   - **동시 시작**: 같은 기준 커밋·REVIEW.md·인수 기준·테스트 증거를 담은 동일한 Task 스펙으로 두 작업자를 한꺼번에 시작한다. A는 `--agent codex --model gpt-6.2-sol --effort high`, B는 `--agent claude --model claude-sonnet-5-5 --effort high`다. 서로 다른 Dispatch이며, 개발 worktree를 그대로 읽게 하고 파일 수정은 맡기지 않는다. 같은 worktree를 동시에 편집하는 작업자는 두지 않는다.
   - **기준은 base에서**: 리뷰 스펙에 기준 커밋(base)과 검토할 커밋 해시를 적는다. REVIEW.md·요구사항·ADR은 **base 커밋의 내용**을 기준으로 삼게 하고, diff가 `.claude/`, `REVIEW.md`, `docs/quality/`, 인수 기준을 바꿨다면 내용과 무관하게 별도 지적(높음)으로 보고하게 한다. 리뷰어는 보고에 검토한 커밋 해시를 적는다.
   - **격리**: 한 리뷰어의 보고·터미널·Task 결과·메시지를 다른 리뷰어의 프롬프트, 메시지, Task에 넣지 않는다. 스펙에 "다른 리뷰어의 보고서·터미널·Task 결과·Run 메시지를 읽지 말고, 자기 보고만 `worker_done`으로 제출한다"를 명시한다. 마스터는 두 `worker_done`이 모두 도착하기 전에 한쪽 내용을 다른 쪽에 전달하지 않는다.
   - **병합과 판단**: 두 보고가 모두 오면 마스터가 지적을 (a) 양쪽 일치(같은 파일·원인), (b) 한쪽만, (c) 상충으로 나눠 정리한다. (b)와 (c)는 마스터가 코드·문서·테스트를 직접 확인해 채택 또는 기각하고 근거를 남긴다. 중요도는 마스터가 다시 판정한다. 채택한 지적만 마스터 정리본으로 구현 작업자에게 전달하고, 리뷰어 원문은 전달하지 않는다. 양쪽이 놓친 문제는 마스터가 직접 확인한다.
   - **리뷰의 유효 범위**: 리뷰 결과는 보고된 커밋 해시에서만 유효하다. 리뷰 중이거나 끝난 뒤 새 커밋이 생겼거나 해시가 다르면 그 결과로 완료 처리하지 않고 새 커밋을 다시 리뷰한다.
   - **라운드 상한**: 리뷰-수정 반복은 최대 3라운드다. 첫 라운드 이후에는 새 diff 중심으로 재리뷰한다. 3라운드 후에도 중요 지적이 남으면 멈추고 접근을 바꿀지 사용자에게 묻는다.
   - **재리뷰**: 수정 diff는 위와 똑같이 병렬·격리로 다시 리뷰한다. 두 리뷰어에게는 같은 마스터 정리본(채택 항목, 수정 내용)만 줄 수 있고 서로의 원문은 주지 않는다.
   - **Codex 보고 전달 막힘**: Codex 작업자가 `worker_done` 전달 승인(샌드박스 `EPERM`, 승인 프롬프트)으로 멈추면 `escalation`이 온다. 이 경우 마스터가 `worker-read --dispatch <id>`로 작업자의 보고 본문(`worker_done`으로 보내려던 내용)을 읽어 그 보고로 취급하고, 결과에 "worker-read로 확보"라고 남긴 뒤 해당 세션을 `worker-release`한다. 승인은 사용자 몫이므로 마스터가 대신 누르지 않는다. 먼저 `docs/development/WORKFLOW.md`의 Codex 규칙이 설치돼 있는지 확인한다.
   - **시작 실패**: 한쪽이 로그인·모델 가용성 문제로 시작하지 못하면 Dispatch 상태와 복구 가이드를 확인하고 같은 Task를 `--retry-of <실패한 dispatch ID>`와 같은 worktree로 한 번 다시 시작한다. 그래도 안 되면 원인과 필요한 조치(예: Codex 로그인)를 사용자에게 알린다. 앱 동작, 로그인, 데이터 권한, 위치, 순위 계산, 세션·토큰 처리가 바뀐 변경은 두 리뷰가 모두 끝나기 전에는 완료로 처리하지 않는다. 그 밖의 변경은 한쪽 리뷰만으로 진행할 수 있으나 결과에 "단일 리뷰"라고 명시한다.
5. 구현 보고를 받으면 `task-list --ready --brief`로 진행 가능한 작업을 갱신한다.
6. 여러 브랜치를 통합하는 경우 먼저 별도 통합 worktree에서 정확한 커밋들을 합치고, 합친 결과에 대해 검사와 최종 리뷰(위 병렬 리뷰)를 한다. 중요 지적은 구현 작업자에게 전달하고 변경된 검사와 리뷰를 다시 실행한다. 현재 권한 및 환경에서 확인하지 못한 것은 결과에 명시한다. 완료된 후보는 검토된 로컬 커밋으로 남기고, main 병합·푸시·배포는 사용자가 해당 작업에서 승인했을 때 진행한다.

## 완료 보고와 재개

- 작업자를 시작한 뒤 턴을 끝낸다. Orca가 보낸 완료·질문 메시지로 재개한다. 채팅에 본문이 오면 처리하고, `check` 명령을 안내받았을 때만 실행한다. 백그라운드 메일을 가져오는 폴링 스크립트는 사용하지 않는다.
- 판단할 수 있는 작업자 질문은 바로 답한다. 실패한 Task는 성공으로 기록하지 않는다. 시작 실패와 재시도는 위 "시작 실패" 규칙을 따른다. 실패 원인을 확인해 가능한 범위에서 고치고, 응답이 불분명한 실행은 버전에 맞는 복구 가이드에 따라 기존 상태를 확인한다.
- 최종 응답에는 수행 작업, 결과 커밋 또는 파일, 검사 결과, 두 리뷰어의 병합 결과(일치·한쪽만·상충, 채택·기각과 근거), 확인하지 못한 항목을 짧게 적는다. 실기기 검증이 남았다면 연결이 필요한 시점을 알려준다.

## 읽기 전용 연결 시험

사용자가 오케스트레이션 자체의 연결 시험을 요청하면 위의 제품 작업 대신 같은 worktree에서 읽기 전용 작업자를 시작한다. Claude 작업자(`claude-sonnet-5-5`, `medium`)와 Codex 작업자(`gpt-6.2-sol`, `high`)를 서로의 결과를 보지 않게 병렬로 시작하고 각자의 `worker_done` 수신 여부를 확인한다. 시작 실패 시 재시도 절차도 시험한다. 시험은 파일 수정 없이 진행하고 두 보고의 수신 여부를 요약한다.
